# テスト設計方針

Minecraft や依存 MOD と接続した処理結果、状態遷移、再発させたくない不具合を GameTest で確認する。実行コマンドと検証範囲は [開発構成](development.md) と [AGENTS.md](../AGENTS.md) に従う。

## 検証範囲と配置

- 操作の入口を選び、生成・消費・保存・復元・終了など、成功を識別できる結果を検証する。拒否ケースでは正常系も用意し、拒否後に資源や状態が維持されることを確認する。
- 定数や getter の転記、登録件数、同じ故障原因を覆う重複テストは増やさない。登録・タグ・データは利用先との接続を検証する。必須データの取得に失敗した場合は assertion で示す。
- テストは `gametest` 配下で機能別に管理する。`gametest.runtime` は依存のロードと混入を確認する。任意連携を追加したときは実際の挙動を対応する機能のテストで検証する。
- 標準構成では任意 MOD なしで成立する挙動を確認し、任意構成では対象 MOD がロードされたことを確認して連携を検証する。不在で意図的に省略したケースは実行済みの成功に含めない。
- 実通信や client の描画・入力・音声は、対象の経路を実際に通した範囲で報告する。client 固有部分は手動確認へ引き継ぐ。

## 安定した準備と観測

- fixture ごとに world の変更と生成物を所有する。GameTest helper の相対座標と Level API の絶対座標を区別し、射線、移動経路、対象の当たり判定を structure に収める。対象は参照、UUID、owner などで識別する。
- 操作は一度行い、待機中は状態を観測する。非同期処理は根拠のない固定 tick を避け、完了条件と期限を使う。到達 tick が仕様の場合は、対象の登録、chunk の読込、実際の tick 進行を検査して期待時刻を守る。
- 乱数分岐が検証対象ならテストが所有する入力を制御する。共有 world の乱数、設定、listener、player、entity を変更した場合は成功・失敗・timeout の全経路で復元または解放する。観測する自然終了と、残存資源の後片付けは別の段階にする。
- 単独起動と全件実行で前提や結果が変わらないようにする。失敗時は必要な前提、対象、実際の状態を診断に残す。同じソースでの再実行と修正後の実行を記録し、単発失敗や少数回の成功だけで不安定性を判断しない。

## 既存テストの整理

独立した故障原因や重要な境界を検出するケースを残す。観測が弱ければ書き換え、同じ経路と故障原因が重複する場合は統合を検討する。複数ケースをまとめる場合は個別に失敗を識別できるようにし、すべての assertion が終わってから成功を通知する。削除・統合時は残る検出経路を説明する。
